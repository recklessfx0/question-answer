# Localization and translation

Design for UI messages, content translations, formatting and locale-aware delivery across web, REST and MCP. Provisional until [ADR 0001](adr/0001-localization.md) is approved; contracts live in `app/Contracts/Localization/` and the work is tracked as the `localization` workstream (`I18N-*`). Requirements that gate this work: SEC-C-07, SEC-C-02, SEC-D-03, SEC-E-01.

The framework ships English. Everything else is installable, switchable and removable at runtime without a deployment.

## Terms

- **Locale** — BCP 47 tag (`en`, `de`, `pt-BR`), normalized to lower case with a canonical subtag case. It selects messages, formats and direction, never content.
- **UI message** — a catalogue string addressed by a stable ID, rendered through ICU MessageFormat.
- **Content translation** — an editorial record of a question, answer or clarification in one locale, with its own revisions and status.
- **Formatting** — dates, numbers, currency, relative time and collation, which follow the locale; timezone follows the user, not the locale.
- **Language pack** — an extension that contributes catalogues only; it ships no PHP.

## Principles

1. Locale input is never trusted. A tag must match `^[a-z]{2,3}(-[a-z0-9]{2,8}){0,3}$`, must be at most 35 characters, and must exist in the installed allow-list before it reaches a path, a file name or a cache key.
2. Messages are data, not code. Catalogue values are ICU patterns; output is escaped by the template layer in context, and no catalogue value is ever evaluated, included or reflected as HTML.
3. Content translation is editorial. Machine output is a draft labeled as such; nothing reaches `published` without a human reviewer who is not the author.
4. The default locale is always 100% complete. A missing key in the default locale fails the build; other locales fall back and report their completeness.
5. No request-path filesystem scanning. Catalogues are resolved by locale and domain from a known map, loaded once and cached; a request never globs a directory.

## Locale negotiation

Resolution order, first match wins:

1. Explicit locale in the path (`/de/…`) or an explicit `locale` parameter — only when it is in the allow-list.
2. The signed-in user's stored preference.
3. `Accept-Language`, parsed with hard bounds: at most 20 ranges, `q` values clamped to 0–1, script and region subtags honored, wildcards ignored.
4. The site default locale.

The fallback chain is bounded to two steps — exact tag, then language-only (`pt-BR` → `pt`) — then the default. There is no chain traversal into unrelated locales and no recursive resolution.

Unknown or disabled locale in a URL returns `404`, not a redirect: a redirect would make one URL serve many variants and poison caches. Public pages never redirect on `Accept-Language`; the header may only drive a dismissible suggestion. The preference cookie is a suggestion, never authoritative for a cached page.

## Message catalogues

Format: one PHP file per locale and domain, returning a flat `array<string, string>` of ICU patterns.

```
resources/lang/en/default.php     question.answer.accepted => "Answer accepted by {editor}."
resources/lang/en/validation.php  validation.required      => "{field} is required."
resources/lang/de/default.php
```

Domains: `default`, `admin`, `validation`, `mail`, `installer`, `mcp`. A domain is lazy-loaded, so an API response never reads admin strings.

Resolution precedence, lowest to highest: core catalogues → installed language packs (by pack precedence) → theme overrides → site overrides stored in the database. Every layer is keyed by the same message ID; a higher layer can replace one key without replacing the domain.

Message IDs are stable and dotted (`question.answer.accepted`). English text is never the key — rewording a message must not break translations.

Caching: catalogues compile into a cache entry keyed by `locale + domain + catalogue version`, versioned by installer, update and any override write. PHP arrays plus OPcache are why the format is PHP and not YAML or JSON: no parser on the request path and no extra dependency on shared hosting.

## ICU message rules

- Named placeholders only: `{count}`, `{editor}`. No positional placeholders, no concatenated sentences, no string building in templates.
- `plural` and `select` cover grammatical number and gender. Plural rules come from the `intl` extension (`MessageFormatter`); without `intl` the installer warns and a reduced fallback renders `other` only — documented, not silent.
- Number, date and time use ICU skeletons or `NumberFormatter`/`IntlDateFormatter`, never `sprintf('%d')` on a localized value.
- Messages contain no HTML. When a sentence must wrap a link or emphasis, the template composes it from separate keys and escapes each part; there is no "HTML in translations" mode.
- Validation: parameters are type-checked against the pattern; an unknown placeholder or a malformed pattern is a test failure, not a runtime surprise. A CI check proves that every key used in `app/` exists in the default catalogue and that every default key exists in each shipped catalogue.

## Content translation model

Content identity is separate from a language variant. A **translation group** groups the same logical question with its per-locale records:

- `translation_group` — stable ID shared by all locales of one item.
- `content_translation` — locale, group ID, node ID, source locale, source revision hash, status, author, reviewer, timestamps.
- Each translated record keeps its own revision chain, editorial state, sources and citations. Votes, bookmarks and reports stay attached to the group, so a reader sees one score regardless of locale.

Translated fields: title, body, clarification text, answer text, summary and slug. Locale-invariant fields: IDs, author identity, timestamps, status transitions, votes, permissions and parent/child structure. Nesting is defined once on the group, never duplicated per locale.

Status: `missing` → `machine_draft` → `draft` → `in_review` → `published`, with `stale` when the source revision hash diverges from the record's stored hash. Editing the source flips dependent translations to `stale`; stale translations stay readable but are labelled and cannot be promoted without a fresh review.

Only a reviewer may publish, a reviewer may not approve their own translation, and every transition is audited. Machine translation is always stored as `machine_draft` with the provider and timestamp recorded, and is disclosed to readers when the locale's content is machine-derived.

Deleting a group deletes its translations; exporting a user's data includes the translations they authored.

## URLs, canonical and hreflang

The default locale is unprefixed (`/questions/42`); every other locale is prefixed (`/de/questions/42`). Slugs are per-locale, so `/{locale}/{slug}` is unique per locale.

- Each locale page declares its own `canonical`.
- Every page returns an `hreflang` set covering all published locales plus `x-default` pointing at the default locale, and cross-links are reciprocal.
- The language switcher preserves route and query, mapping the current node to its translation group and falling back to the group root when a translation is missing.
- Only published translations appear in `hreflang`; a missing translation is a `404` in that locale, not a redirect into the default locale.
- Locale prefixes are part of the cache key, so a cached page never varies by header.

## Formatting

Dates and times are stored in UTC and rendered in the viewer's timezone; the locale chooses the format, the timezone is a separate user setting. Numbers, currency, percentages, relative time ("3 days ago") and lists go through `intl`. Collation for displayed sorted lists is locale-aware; search normalization is separate and never reuses collation rules. First day of week and 12/24-hour preference come from the locale with a user override.

## Right-to-left and bidirectional text

Direction is a property of the locale table, applied as `dir` on `<html>`; layout uses logical CSS properties so no component is mirrored by hand. User content is isolated (`dir="auto"`, `<bdi>`), numbers and code stay left-to-right, and icons with direction (arrows, chevrons) swap. Bidi control characters (U+202A–U+202E, U+2066–U+2069) are stripped from user input and from translation imports: they can make one string render as another and are a spoofing primitive, not a feature. The v0.3 RTL and keyboard task owns the visual verification.

## Caching and performance

- HTML cache keys use the canonical URL, which already contains the locale.
- `Vary: Accept-Language` is sent only from endpoints that actually negotiate a header (JSON-negotiated content), never from cacheable HTML.
- Catalogue memory is bounded: at most two locales in one request (requested plus fallback), one domain per controller, and no eager load of all domains.
- A translation expansion budget applies to layout: German and Finnish run long, and the design system must not truncate at 1.0× English width.
- Page cache entries are invalidated per locale on publish, so a translation does not flush the whole site.

## API, MCP and AI

- REST read endpoints accept `locale` as a query parameter and otherwise negotiate `Accept-Language`; responses carry `Content-Language` and `Vary` when negotiated.
- Payloads expose translation metadata: requested locale, resolved locale, whether a fallback was used, translation status and source locale. A client can therefore distinguish "English because the content is English" from "English because German is missing".
- Write endpoints require an explicit locale; a missing one is a validation error, never a guess.
- MCP read tools take a `locale` argument; resources return the same metadata. MCP write tools may submit a translation draft but cannot publish it.
- AI draft generation takes the target locale as an input and returns `machine_draft` content with provenance; retrieval prefers the requested locale and falls back to the source locale with disclosure. Private content is never sent to an external translation provider without explicit consent, and provider credentials follow SEC-E-03.

## Language packs

A language pack is an extension of type `languages` in the existing extension lifecycle. It contributes catalogues, a locale metadata file (direction, plural rules reference, display name, date patterns) and a manifest declaring the locale tag, domains and version. It is data only: no entrypoint, no PHP, no hooks, and it executes nothing.

Packs are signed and verified like any other extension, are subject to precedence, and are removable without leaving stale keys. Two packs claiming the same locale and key produce a reported conflict resolved by declared precedence, never by load order. Core locale metadata stays authoritative for direction and number systems unless a pack is explicitly allowed to override it.

## Import and export

Content translations exchange as XLIFF 2.0 — the format translation tooling already speaks — with stable unit IDs derived from the translation group and field. UI catalogues export as PHP arrays and import after validation: keys must exist in the default catalogue, patterns must parse, and bidi controls and HTML are rejected. Exports are deterministic so a review diff shows only real change. CLI tooling lives under `tools/` and runs from a maintainer machine, never on production.

## Administration

The localization panel lists installed locales with enable/disable, default (one, not deletable while referenced), completeness per domain, per-locale reviewer assignment, a stale-translation report, catalogue editing for site overrides, and XLIFF import/export with a dry-run preview. Changes are audited and cached entries are invalidated per locale.

## Security

- Locale tags are validated against the allow-list before any path, file, cache key or header use; the locale is never concatenated into a `require` path without that check (SEC-C-07).
- `Accept-Language` is parsed with bounds and rejects CR/LF and control characters, so a crafted header cannot inject response headers or memory-exhaust the parser.
- Catalogue strings are treated as data: escaped at output, never `eval`ed, never rendered as raw HTML.
- Bidi controls are stripped from input and imports; a translation cannot visually impersonate another string.
- Publishing translations is a privileged, audited action; the four-eyes rule and machine-draft labelling defend against translation poisoning (SEC-D-03).
- Machine translation is a data-egress path: it is opt-in, it discloses what leaves the server, and private content requires explicit consent (SEC-D-02).

## Testing

- Contract tests for `Translator`, `LocaleResolver` and `CatalogueLoader`.
- Unit tests per shipped locale: plural categories, `select`, number and date skeletons, and the fallback chain.
- Negative tests: unknown locale, disabled locale, malformed and oversized `Accept-Language`, CRLF injection, missing key, malformed ICU pattern, bidi controls in input.
- Pseudo-localization in CI: every default message rendered with accents and 40% expansion to expose truncation and hard-coded strings.
- Completeness gate: default locale 100%; other shipped locales fail below an agreed threshold, warn above it.
- RTL snapshot tests per component, and hreflang reciprocity checks in the HTML test suite.
